## 2. CLI (`npm run lab:m1 -- <command>` = `lab/m1/cli.ts`)
`observe`, `completeness`, `provenance`, `accept`, `campaign`, `commitment`, `canary`, `thresholds`, `seal`, `verify-seal`. Exit codes: 0 positive, 10 reject/invalid/failed, 20 incomplete/unset, 30 error, 64 usage. One canonical-JSON line; only `record` (the new evidence run id) varies between identical inputs. Every command takes explicit paths, derives the canonical identity from the SERVER package (never a directory name or supplied artifact), reads inputs only, and calls the existing function (`writeObservationResult`, `writeProvenanceResult`, `m1AcceptRun`, `m1LocalCampaign`, `buildCommitment`, `verifySeal`). `accept` and `campaign` recompute from the authoritative inputs; a supplied PASS artifact only agrees or disagrees. The `AcceptCli` type stays "ids and input locations only" (a pinned assertion): the verifier's heartbeat limit travels as a separate `VerifierSettings` argument.

## 3. Off-host observers
Done in code: the collector binds results to the run and campaign, records request-level receipts with a gapless sequence, beats a heartbeat, and writes a closing declaration (counts, last sequence, covered window, heartbeats); `run.ts` records the run window; the canary and collector accept host and port settings (loopback by default) so they can run on separate machines; the completeness check is part of the observation component (`observation-bundle.ts`), with the heartbeat limit supplied by the VERIFIER. Not done: nothing is launched remotely; the collector and canary have never run off-host.

**What genuine independence requires (separate processes are not enough):** (1) the observers' project, service accounts and groups share nothing with the target and generator principals, and no principal in A holds any role in B (`iam.tf`); (2) observer credentials are not readable from the target or generator hosts, and there are no service-account keys; (3) observer evidence is written create-only to storage that A can neither overwrite nor delete, under a prefix only B can write; (4) the custodian (C), a third principal, seals it, and A cannot read B's raw records before sealing; (5) the verifier runs under C or the owner, recomputes everything, and takes the heartbeat limit from the pre-run commitment, not from the observer; (6) observer images are built and pinned separately from the target image; (7) the canary's address is not in the generator's range; (8) the clocks used for coverage are compared at the start (`clockAgreementMs` in the level definition). Items 1 to 3 are written in Terraform; 4, 5 and 8 are procedures; 6 and 7 are owner decisions.

## 4. Commitment and sealing
Flow (all local, tested end to end): identity of the server package, `commitment` verification (rebuilt by the same builder, digest and run, campaign and commit compared with the package), observers, `seal` (create-only copy plus `SEAL.json`: SHA-256 and size of each observer file, run, campaign and commitment digest), `verify-seal`, inventory and provenance (existing verifiers), `accept` with `--require-seal`, `campaign` with `--require-seal` (also checks the seals of the three runs are distinct). Post-finalization modification, a missing file or declaration, a replayed seal and a cross-run substitution each stop the run (tests). **Byte consistency is separate from producer authentication:** the seal states `producerAuthentication: "none"`, `verified: false`; nothing here proves who wrote the bytes. No signing key was created and no retention lock was activated. Re-sealing modified bytes yields a self-consistent seal, but the recorded result no longer matches the recomputed one, so the run is not accepted; only the independent custodian writing the seal digest somewhere the producer cannot change closes that gap.

## 5. Budget and emergency stop
Reviewed with fakes only (no deletion, no billing change). Verified in tests: selection requires both exact labels (missing, empty, wrong-typed or foreign labels are never selected; a run-scoped stop needs a run id); a failing or hanging target does not prevent the others; repeated execution is harmless; a deletion that does not finish, or a labeled instance that returns, is reported as remaining and makes the handler fail so the event is redelivered; missing price inputs and an unverified exchange rate are "not bounded".
What each layer is: **estimated spend** about 50 TRY per run under ASSUMED prices (`infra/m1/cost-ledger.json`); **provider budget alerts**: notifications that lag billing and stop nothing; **enforced limits**: the vCPU quota and `max_run_duration` (provider side, unexercised); **automated shutdown**: reaper and budget stop (unexercised against a real project); **residual after shutdown**: orphaned disks if auto-delete fails, logs, the evidence bucket for its whole retention, the function and scheduler while the stack exists. `assessCostBound` returns `strictlyBounded: false` for the current ledger: no component is verified and egress, logs and storage have no enforcement. **Spending is therefore not claimed to be strictly bounded**; the structural estimate is far below the 750 and 3,000 TRY planning limits, which are planning limits and not proof of a hard cap.

## 6. Canary baseline procedure and threshold record
Contract unchanged and enforced: 100 percent of journeys in all three phases; any unexpected 429, challenge, timeout, transport failure, error status or false rejection fails; named operational actions required. `infra/m1/canary-thresholds.template.json` is the record where the owner fixes numbers: every value is `null` (UNSET), nothing was invented; `validateOwnerThresholds` accepts only an approved record with three distinct baseline measurement ids and ordered positive percentiles per phase, a recovery time, a heartbeat limit and named actions; `evaluateLatencyAgainstThresholds` is inert (NOT_EVALUATED) until then.
**Baseline measurement procedure (before the campaign, not qualification evidence):** (1) on three separate fresh instances from the pinned image, with no generator running, run the canary journey at least N times each (N is an owner decision; the level uses 12 baseline journeys at 4 s spacing); (2) record per step p50, p95, p99 and the run-to-run spread; (3) measure the canary-to-target round trip with no application work and the canary scheduling lag and clock error; (4) run one rehearsal attack window (`--dry-run`/rehearsal level, labelled not qualification) and record window and recovery percentiles and the time to return to the baseline spread; (5) the owner chooses maxima above the observed spread, enters them with the three baseline evidence ids, approval reference and date, and runs `thresholds --file` until it exits 0; (6) the digest of the FIXED record goes into the pre-run commitment. The defense telemetry gap tolerance (`gapToleranceMs`) and the observer heartbeat limit remain separate numbers.
