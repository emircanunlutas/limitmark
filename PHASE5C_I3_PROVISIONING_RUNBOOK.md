## Lifecycle operator procedure (after all prerequisite gates)

The only reviewed intended chain is offline sign -> sealed artifact -> pinned local CLI -> private R2 request mailbox -> scheduled mailbox -> durable guard -> executor -> lifecycle-only admission -> authority atomic receipt. The observer separately reads through AuthorityLifecycleReadOnly and writes a bounded reconciliation result. The raw templates are not commands to deploy. Production CLI uses the exact pinned deployment/lifecycle-transport.production.json rendered copy after preflight; no target URL, Worker name, method or account override.

1. Offline signer verifies exact operation, environment, authority, epoch, release/key IDs, freshness and explicit Production intent. Use the quiet preparation and explicit UTF-8-without-BOM file procedure above. Never put the private key or sealed JSON in CLI arguments/logs. For Production, both preparation and submission require their respective explicit Production confirmation flags. Staging must use a separately reviewed staging toolchain, not these Production-pinned scripts.
2. Local operator parses bounded sealed-file metadata with npm run authority:init:submit -- --command <protected-file> --confirm-production --inspect (or npm run authority:rotate:submit with the same flags). This read-only inspector prints INSPECTED, operation, environment, authorityId and policyEpoch. It **does not load the manifest or verify signature authenticity**. Preserve the sealed file. The non-inspect submission path subsequently loads the pinned manifest and verifies the signature before its PUT. The CLI reports canonical command digest and raw-file SHA-256 after its one PUT attempt; record both in a protected journal even if transport is ambiguous. Canonical identity is the digest of the command, not the R2 object key or raw-file hash.
3. Once, use npm run authority:init:submit -- --command <protected-file> --request-credentials <protected-credential-file> --confirm-production (or authority:rotate:submit). It sends one bounded S3 PUT to initialize.json or rotate-release.json and returns UNCONFIRMED even on an accepted upload; acceptance is storage evidence, never commit evidence. Do not retry the PUT, re-sign, make a replacement command, overwrite a pending slot, use a second operator, or start another lifecycle action while outcome is uncertain.
4. npm run authority:result -- --kind lifecycle --digest <64-hex-digest> --result-credentials <protected-result-credential-file> is a **read-only R2 GET**. It validates the bounded result and displays either SUCCESS/ALREADY_APPLIED with digest and receipt, or UNCONFIRMED with a reduced observation. A missing, malformed or mismatched result is UNCONFIRMED. Only a positive exact receipt may justify settlement. No force, rearm or reset exists.
5. After exact positive receipt, npm run authority:settle -- --digest <digest> --request-credentials <protected-credential-file> --confirm-production is a **control/lifecycle mutation**: it PUTs settle.json and may release the guard supervisor latch. Read the settlement result with npm run authority:result -- --kind settlement --digest <digest> --nonce <returned-nonce> --result-credentials <protected-result-credential-file>. Require confirmed SETTLED after exact positive receipt **before another supervised lifecycle command**. A REQUESTED control PUT alone is insufficient. Settlement never deletes/reopens a consumed claim and is not lifecycle commit proof.

No wrangler tail, remote dev, temporary HTTP endpoint, public bearer route, manual DO SQL, dashboard mutation or direct RPC improvisation is a submission mechanism. A failed provider call after a durable guard claim can leave the claim consumed **before any executor call**. Actual non-execution in a fault test does not grant the real operator a retry or a rollback certificate.

## Authoritative reconciliation and suspension

On upload timeout, ambiguous HTTP status, schedule delay, lost result, executor/admission exception, revoked reader token or any UNCONFIRMED status, preserve the sealed file, reported canonical digest/raw hash if available, CLI output and local timestamps. Freeze further lifecycle commands for that environment. Do not re-sign, create a replacement command, submit again, clear the slot, rearm the guard or infer rollback from a negative transport observation. If the reader/reconciliation path is unavailable, preserve available evidence, stop new uploads, suspend mutation processing where safely possible and retain read-only observation where possible; **do not delay containment indefinitely** waiting for reconciliation.

npm run authority:reconcile -- --digest <digest> --request-credentials <protected-credential-file> --confirm-production is a **provider mutation**: it PUTs reconcile.json with a new nonce. The authority operation triggered later through the observer is read-only. The CLI prints REQUESTED or UNCONFIRMED with operation, digest and nonce; it does not return authority state. Preserve that output. Then use the **read-only R2 GET** npm run authority:result -- --kind reconciliation --digest <digest> --nonce <returned-nonce> --result-credentials <protected-result-credential-file>. Preserve its printed JSON and timestamps. Do not confuse REQUESTED with an observed receipt.

The result verifier internally enforces an at-most-8,192-byte strict UTF-8/JSON schema, result version, Production environment/authority/epoch, requested digest/nonce, bounded observation freshness, and receipt shape including key fingerprint, sequence and release fields. For a positive reconciliation it prints SUCCESS, digest and the full validated receipt object. For a negative reconciliation it prints UNCONFIRMED, digest and observation: NOT_FOUND, HISTORY_INCOMPLETE or UNAVAILABLE. It **does not print** the negative observation's initialized flag, coverage or release array; it also does not expose raw R2 bytes, result schema/version, observation timestamp, account ID, or the nonce after verification. The operator can compare the positive receipt's displayed digest, environment, authorityId, policyEpoch, keyFingerprint, release IDs and sequence to the sealed command and separately reviewed manifest/key inventory; the CLI has already validated the requested nonce internally. The displayed receipt is transport data validated by the CLI, not an independently signed attestation. The operator must independently retain deployed reader-binding/version evidence from the pre-initialization gate before trusting it.

**CLOSED / TOOLING REQUIRED:** any later acceptance gate demanding direct operator inspection of negative coverage, uninitialized or current release arrays, raw result bytes, observation time, or guard-claim contents cannot pass with the current CLI output alone. Use only a separately reviewed evidence acquisition tool and re-review that gate; do not use manual SQL, dashboard authority internals, temporary HTTP, direct RPC or mutation. The operator may preserve command artifact, CLI stdout/stderr, digest/raw hash after submission, nonce from the reconcile request, displayed positive receipt and settlement output directly. If the digest was not reported before a failed pre-PUT validation, preserve the artifact and treat digest evidence as unavailable until a reviewed local derivation exists.

An exact positive receipt with matching command digest and target proves that command committed atomically with authority state, even if the current release later changes. Require confirmed positive settlement before another supervised lifecycle command. NOT_FOUND while execution could be in flight remains UNCONFIRMED; negative output does not prove an uninitialized authority or complete receipt coverage to the operator. HISTORY_INCOMPLETE is a recovery gate: stop all lifecycle processing and preserve evidence. UNAVAILABLE remains UNCONFIRMED. Invalid result schema, wrong nonce/digest/environment/authority/epoch or unverified reader binding also remain UNCONFIRMED. Negative evidence never releases the supervisor latch. A token revocation or Cron disable cannot retract stored input. Recovery from suspected PITR/reset or missing history follows PHASE5C_I2_OPERATIONS.md state-loss drain and separate review; it never edits the guard and authority independently.

Safe suspension: preserve available evidence and attempt reconciliation when available; stop new uploads immediately, revoke request-write credentials where warranted, then suspend future schedules/mutation processing where safely possible while retaining read-only observation. Keep durable guard claims and authority receipts intact. Schedule suspension after possible dispatch is availability control, **not rollback**. Never describe deleting a guard claim, restoring the guard alone, clearing an authority receipt, resetting a DO, rearming a command or deleting R2 input as rollback.

## Cost and retention

Normal lifecycle traffic is small; proposed one-minute mailbox and observer polls are about 43,200 scheduled invocations each, 86,400 combined, per 30-day month per environment before other requests. R2 storage/Class A/Class B operations, Cron/Workers CPU and requests, guard and authority SQLite DO requests/duration/storage, existing Cloudflare Access/Workers and Vercel P/Q build/protection usage all need actual account-plan and quota verification at gate 1. Do not treat published generic pricing as this account's entitlement. Stolen request-bucket credentials can create storage/operation costs even though Workers read only bounded fixed keys; use scoped credentials, provider budgets/alerts, rotation/revocation and lifecycle cleanup. Result retention is 30 days; command/receipt history must not be pruned merely to meet R2 retention or cost targets. PostgreSQL and Turnstile are **not required** for private I3 qualification; public persistence remains closed.
