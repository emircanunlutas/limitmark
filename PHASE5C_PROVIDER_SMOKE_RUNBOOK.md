# Phase 5C: later manual Upstash and ingress smoke

Not executed. This checkout has no Upstash adapter or proxied identity implementation. These checks are a later acceptance procedure, not instructions to enable the current gates. Public persistence remains off throughout. Use no customer data, no production database and no real submission/Turnstile/origin credentials in logs.

## Prerequisite: resolve the contract first

Before using Upstash for strict admission, obtain authoritative clarification guaranteeing combined-rule consistency and preservation of acknowledged observations across failover/partitions. The current published eventual-consistency guarantee is insufficient; see [the review](PHASE5C_SECURITY_REPORT.md). If that cannot be established, stop provider qualification and select a different architecture. A successful Lua/concurrency smoke cannot override this prerequisite.

Likewise, require documented application-consumable authenticated visitor identity under the selected Vercel proxy offering, including direct-origin and Worker behavior. Lite alone is not qualified. Preserve origin-secret authentication as a separate layer. Do not infer approval to purchase, onboard, change DNS or deploy from this document.

## Isolated fixture and connectivity

1. After separate authorization, provision a disposable provider database used only for this qualification. Record provider version/topology, region/read replicas, durability, eviction, permissions and the supporting consistency commitment. Use a separate restricted operator account/token and a test namespace such as `limitmark:smoke:pre`/`limitmark:smoke:post`. Do not reuse a production resource or HMAC secret.
2. Use the reviewed adapter in an isolated harness; keep the website's registry and persistence gate closed. This harness will need to be supplied with that implementation. Server-only values use the official names `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN`. Verify a strict HTTPS origin, certificate verification, no embedded URL credentials/query/fragment/path surprises, no redirects and no credential logging. Reject missing/malformed/example values before any network call.
3. Issue an authenticated `PING` through the same HTTPS transport. Expect only the documented success result; wrong/missing token, HTTP errors or malformed JSON must become unavailable. Do not put the token in a URL, terminal argument, screenshot or test report. Record only aggregate outcomes and latency.
4. Verify `TIME` and an EVAL that calls `TIME` using the provider's actual deployed version. Confirm seconds/microseconds parsing and clock/failover guarantees needed by the reviewed algorithm. Do not substitute a browser or function clock.

## Run the exact reviewed admission operation

5. Record the exact script hash/version and declared key set. Use fixed fixture namespaces, synthetic HMAC-derived client values and internally generated attempt members. No actual IP, email, inquiry UUID, form data, origin secret or submission/challenge token may enter keys or values. Test with small capacities, e.g. client 2/global 3, and a 2-second window.
6. Verify client and global acceptance together. Seed a saturated global rule with a different fixture client; denied admission must leave the new client's count unchanged. Reverse the case: a client denial must not consume global capacity. Compare counts/observations using the provider's primary-consistent inspection method, not a stale replica.
7. Submit at least 50 simultaneous requests from independent harness clients against a global capacity of 7 (window longer than test execution). Exactly 7 may succeed, with 7 distinct recorded attempts; same-timestamp attempts must remain distinct. Repeat contention against a shared client key and inspect every participating rule. Include different execution regions only if they are in the reviewed supported topology.
8. Exercise the exact interval `(t - W, t]`. In an isolated fixture script/harness using server time, seed observations at the lower boundary and immediately inside it; boundary observations must expire, inside observations must count. Record the evaluated server timestamp and result only. Also verify production code does not accept caller-controlled timestamps. With the actual unmodified admission script, test acceptance before/after the rolling expiration rather than assuming a fixed calendar boundary.
9. Inspect `PTTL` after an acceptance: positive and bounded by the reviewed retention policy. Denials must not extend old consumption indefinitely. Stop traffic, wait beyond the largest fixture TTL, then confirm exact fixture keys are absent. Verify expired observations are removed during active traffic too. Never use FLUSHDB, KEYS over a shared database, or broad deletion; prefer automatic TTL cleanup.
10. Send malformed/empty/duplicate/oversized key/rule collections, nonpositive/noninteger/unsafe limits and windows, and wrong-type fixture keys. Require unavailable before mutation where applicable. Check all rules for unchanged quota and ensure error text never exposes keys/credentials. Review storage-pressure/runtime errors as well: script isolation does not imply rollback of arbitrary failures.

## Failure, privacy and environment checks

11. Use a harness-controlled transport fault to drop the HTTP response after the server accepts the script. Assert one network dispatch, unavailable, no Turnstile/DB continuation, and no automatic retry/refund. Read fixture state separately to verify consumption may already exist. Repeat with pre- and post-stage faults. Distinguish a caller timeout from cancellation of server execution.
12. Test timeout, connection failure, non-2xx, invalid/missing result, truncated body and provider rejection. No response may become allowed through SDK timeout defaults, caches or fallback. Verify actual SDK/HTTP retry settings; fail the smoke if one consuming attempt can be retransmitted without proven idempotency.
13. Inspect the provider dashboard with synthetic fixtures only. Key/value contents must obey the allowlist above. Disable identifier analytics and optional SDK telemetry; avoid MONITOR or command logs containing sensitive data. Review provider retention, backups, account access and any unavoidable service-side command/key capture. Record aggregate results only; do not export full keys.
14. Confirm every physical key uses the correct fixed resource/environment/stage namespace. Test copied credentials in Preview/development: production adapter must not construct or send any request. Verify mismatched/absent Vercel metadata, intake mode, ingress policy, origin, Turnstile or DB gates deny. Use separate resources/ACL-scoped credentials; a namespace is not a resource-level security boundary.

## Real ingress and complete admission (separately authorized)

15. Use an isolated protected fixture route that returns only neutral decisions or in-memory equality checks, with no header/IP dump, durable logs or database write. From two controlled networks, compare HMAC equality internally: stable for equivalent addresses, different for distinct addresses. Confirm the reviewed Cloudflare-routed identity is the controlled visitor, not shared egress. Capture no raw IP in the report or Redis. Do not deploy this diagnostic route as an unprotected header echo.
16. Compare ordinary proxied traffic, direct Vercel deployment/custom-domain access, and direct requests supplying CF-Connecting-IP, CF-Connecting-IPv6, True-Client-IP, XFF, X-Real-IP, X-Vercel-Forwarded-For, CF-Ray and forged Host/Origin. Repeat direct attempts with the disposable origin bearer deliberately supplied: it must still not permit forging visitor identity. Missing bearer must deny when origin protection is required.
17. Test Worker-mediated same-zone/cross-zone/non-Cloudflare paths and Pseudo IPv4 off/add/overwrite only in separately authorized disposable zones. Unsupported shapes and contradictory/multi-hop values must close. Confirm Advanced/platform-protected headers actually meet the reviewed contract; mere presence of a CF header is insufficient.
18. Use synthetic Turnstile outcomes in the harness to verify pre → verification → post → a counting persistence stub. Rejected/unavailable verification spends no post quota; pre outage stops verification; post denial/outage stops the stub. Replay/corrected submissions retain the existing token semantics. Edge flags and origin possession cannot skip stages. Public intake disabled must still leave independently authorized admin fixtures available.

Retire the disposable resources/credentials after separately authorized cleanup. Retain script/version/topology, timestamps, aggregate counts, error categories and TTL results, without secrets or customer data. Re-run the required DB gate and application regressions before any later launch review. None of these tests can prove a guarantee the provider/platform does not make.
